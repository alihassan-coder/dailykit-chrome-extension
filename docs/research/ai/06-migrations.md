# 06: Migrations without a server (Neon + local stores)

Researched 2026-11-01. Context:

- The extension background is the only thing that talks to Neon, using `@neondatabase/serverless` **1.2.0** `neon()` over HTTP (root doc `docs/research/06-neon-from-mv3.md`).
- Several devices, and possibly several users (doc 05), share one database. They may run **different extension versions** at the same time.
- Store policy: all SQL must ship inside the package. Never fetch migrations remotely (CWS remote-code rule, root doc 06).

## 1. What the HTTP driver allows

From https://github.com/neondatabase/serverless/blob/main/CONFIG.md and https://neon.com/docs/serverless/serverless-driver:

- `sql.query(text, params, opts)` runs one parameterised query, which is one `fetch`.
- `sql.transaction([q1, q2, …], { isolationLevel?, readOnly?, deferrable? })` runs a **single non-interactive transaction**: all statements are sent together, so you cannot branch on a result mid-transaction. If any statement errors, everything rolls back.
  - The docs inconsistently call the isolation key `isolationMode` in prose and `isolationLevel` in the example. Check the TypeScript types.
- No sessions over HTTP, so **session advisory locks (`pg_advisory_lock`) are useless**: the lock dies with the request. **Transaction-scoped `pg_advisory_xact_lock(k)` works** as the first statement of a `transaction()`, because the whole array runs in one backend transaction. This is inferred from Postgres semantics and the "single transaction" wording; spike it.
- Each array element should be **one statement**. Splitting a migration into statements is the runner's job. It is unverified whether a multi-statement string without params is accepted over HTTP, so do not rely on it.
- 64 MB request limit. The service worker dies if a fetch takes more than 30 s, so apply **one migration per transaction**.

## 2. Existing tools, checked against these limits

| Tool | What it does (from source) | Usable at runtime in the extension? |
|---|---|---|
| `drizzle-orm` 0.45.4, `neon-http/migrator.js` | `readMigrationFiles()` uses **`node:fs` and `node:crypto`**. It applies each statement with separate `execute` calls, **no transaction**, **no lock**, and only compares `created_at` of the last row (no checksum verification). The pg-core dialect's `migrate` wraps in `session.transaction`, but the neon-http one does not. | **No.** It needs Node, and a crash mid-migration leaves a half-applied schema. |
| `drizzle-kit` 0.31.11 `generate` | Diffs a TS schema and writes `NNNN_name.sql` plus `meta/_journal.json`. Statements are separated by `--> statement-breakpoint` (`breakpoints: true` by default). `out` sets the folder. Docs: https://orm.drizzle.team/docs/drizzle-config-file | **Yes, as a dev-time generator.** The output is plain SQL that a tiny runner can split on the breakpoint marker. Optional. |
| `node-pg-migrate` 9.0.0 | Table `pgmigrations(id, name, run_on)`. **Session** `pg_advisory_lock(7241865325823964)`, no checksums, Node `pg` client. | **No** (Node, TCP, session lock). Its patterns are worth copying: a fixed lock id, a name-ordered table and a per-migration transaction. |
| PGlite (`@electric-sql/pglite`) | Postgres compiled to WASM | Good for **vitest** tests of the SQL files. Unverified that pgvector works in it; design B in doc 05 does not need pgvector. |

**Verdict:** use a **tiny in-house runner** of about 150 lines. Write the SQL by hand. drizzle-kit may draft the SQL if you later adopt Drizzle for typed queries. Don't adopt Drizzle just for migrations.

## 3. Recommended Neon runner

### File layout

```
packages/db/
  migrations/neon/
    0001_init.sql            -- schema toolbelt, user_key table
    0002_memory.sql          -- memory_item, memory_history, memory_message (doc 05)
    0003_….sql
  src/neon/
    client.ts                -- neon(connString, { disableWarningInBrowsers: true })
    migrations.ts            -- import.meta.glob('../../migrations/neon/*.sql', { query: '?raw', import: 'default', eager: true })
    migrate.ts               -- the runner (below)
  src/local/
    idb.ts                   -- openDB(name, LOCAL_DB_VERSION, { upgrade })
    idb-migrations.ts        -- ordered upgrade steps
    data-migrations.ts       -- post-open async steps (decrypt/re-encrypt etc.)
  test/
    neon-migrations.test.ts  -- apply all to PGlite; assert idempotent second run
    migrations-frozen.test.ts-- checksums of shipped files match a committed lock file
  migrations/neon.lock.json  -- { "0001": "sha256…", … } generated by a script, committed
```

File rules:

- Name files `NNNN_snake_name.sql`, with a gap-free version number.
- Split statements on `--> statement-breakpoint`, which is drizzle-kit compatible.
- No `BEGIN`/`COMMIT` in the files.
- **Shipped files are immutable.** The `migrations-frozen` test fails CI if an applied file's hash changes. Fix mistakes with a new migration.

Vite `import.meta.glob` with `?raw` bundles the SQL as strings into the IIFE background. This satisfies the CWS rule that all code ships in the package.

### Tracking table, created by the runner as an idempotent bootstrap

```sql
CREATE SCHEMA IF NOT EXISTS toolbelt;
CREATE TABLE IF NOT EXISTS toolbelt._migrations (
  version     int PRIMARY KEY,
  name        text NOT NULL,
  checksum    text NOT NULL,            -- sha256 hex of the file text (WebCrypto subtle.digest)
  applied_at  timestamptz NOT NULL DEFAULT now(),
  applied_by  text                      -- extension version + random device id, for debugging
);
```

### Algorithm, `migrate(sql)`

1. **Bootstrap:**
   ```ts
   sql.transaction([
     sql`SELECT pg_advisory_xact_lock(${LOCK_ID})`,
     CREATE SCHEMA…,
     CREATE TABLE IF NOT EXISTS…,
   ])
   ```
   `LOCK_ID` is one fixed bigint constant for Toolbelt.
2. **Read state:** `SELECT version, checksum FROM toolbelt._migrations ORDER BY version`.
3. **Verify:**
   - For every applied version that is also bundled, compare the checksum. On mismatch, **stop** with a surfaced error. Never auto-repair.
   - If the database has a version higher than the newest bundled one, this build is older than another device. Run in **compatible mode**: keep syncing only if `db_version ≤ build.maxCompatible`, otherwise show "Update Toolbelt to keep syncing". That limit is a constant per release; see the expand/contract rule.
4. **Apply each pending migration `m` in ascending order, one HTTP transaction each:**
   ```ts
   sql.transaction([
     sql`SELECT pg_advisory_xact_lock(${LOCK_ID})`,
     sql`SET LOCAL lock_timeout = '5s'`,
     sql`SET LOCAL statement_timeout = '20s'`,
     sql`INSERT INTO toolbelt._migrations (version, name, checksum, applied_by) VALUES (${m.version}, ${m.name}, ${m.checksum}, ${device})`,
     ...m.statements.map(s => sql.query(s)),   // raw DDL, no params
   ])
   ```
   - The **tracking INSERT comes first, under the lock.** If another device committed `m` in the meantime, the INSERT hits the primary key, the whole transaction rolls back and nothing runs twice. The runner treats a `23505` error on `_migrations` as "already applied" and returns to step 2.
   - DDL is transactional in Postgres, so a failed migration leaves no trace.
   - The `SET LOCAL` timeouts keep the request well under the 30 s service-worker fetch limit.
   - **Avoid statements that cannot run in a transaction:** `CREATE INDEX CONCURRENTLY`, `VACUUM`, and using a new enum value in the same transaction that adds it. At a few thousand rows a normal `CREATE INDEX` takes milliseconds.
5. Save `neonSchemaVersion` locally (WXT storage item). Memoise "migrated this worker lifetime" so later syncs skip steps 1–4 (one cheap `SELECT max(version)` per sync is enough).

**Triggers:**

- When the user enables sync, or saves or changes the connection string ("Set up database").
- On `runtime.onInstalled` with reason `update`.
- Lazily before the first sync after a worker start.

Never run it from content scripts or pages.

**Expand/contract rule:** devices update at different times, so every migration must keep the **previous release** working.

- Allowed: add a table, add a nullable column or one with a default, add an index.
- Destructive changes (drop or rename a column, add NOT NULL without a default) ship as a separate "contract" migration **one release later**, after the code stops using the old shape.
- Encode the rule as a review checklist in `packages/db/migrations/neon/README` (optional) or in the PR template.

**Encrypted data cannot be migrated in SQL.** The server only sees ciphertext, so content changes such as a new payload shape or a re-embed are **client-side data migrations**:

- Each encrypted payload carries `{ "s": <payloadSchemaVersion> }` inside the plaintext.
- Readers upgrade old shapes on read (lazy) and write back the new shape on the next update.
- Bulk jobs, such as re-embedding after a model change, run as resumable background tasks. They record progress in a per-user row: `toolbelt.user_job(user_id, job, cursor, done_at)`, added in a migration.

**Privileges:**

- The runner needs DDL rights on schema `toolbelt`. The root doc 06 suggests a dedicated role. Make that role the **owner** of the `toolbelt` schema in the one-time "copy setup SQL" step that the user runs as `neondb_owner`.
- Design B (doc 05) needs no `CREATE EXTENSION`. Option A (pgvector) does, so put `CREATE EXTENSION IF NOT EXISTS vector` in the setup SQL rather than in a migration.

## 4. Local stores

### `chrome.storage` items (settings, keys metadata, cursors)

Use WXT's built-in item versioning (https://wxt.dev/storage.html):

```ts
storage.defineItem('local:settings', { fallback, version: 3, migrations: { 2: v1 => …, 3: v2 => … } })
```

- WXT tracks the version in a `v` meta key, assumes version 1 when it is missing, runs migrations as soon as `defineItem` is called, and makes `getValue`/`setValue` wait for them to finish.
- Migrations must be pure, synchronous-safe transforms.
- Define items once, in a shared module imported by the background. Pages that import it run the same migration, and the result is idempotent because of the `v` meta key. Unverified behaviour if two contexts race on the first run, so let the background own writes.

### IndexedDB (cache, outbox, vector matrix)

Use `idb` **8.0.4** `openDB(name, VERSION, { upgrade(db, oldVersion, newVersion, tx) {...} })` with a fall-through `switch (oldVersion)` of numbered steps (case 0, case 1, …).

- **Do not `await` non-IDB promises inside `upgrade`.** WebCrypto, `fetch` and `chrome.*` calls let the versionchange transaction auto-commit. Inside `upgrade`, only change stores and indexes and do cheap synchronous row transforms.
- Anything that needs decryption goes in `data-migrations.ts`. It runs after open, tracks a `dataVersion` in a `meta` store, and is resumable.
- **Cache stores may be dropped and rebuilt** by re-pulling from Neon, which is the source of truth. The **outbox store must never be dropped**: it holds unsynced writes. Migrate it in place. You cannot drain it with the old code first, because by `onInstalled` with reason `update` the new code is already running.
- Handle `blocked` and `versionchange` events: close old connections in open extension pages so the background's upgrade is not blocked.

## Recommendation (one design)

1. Write hand-written, immutable, numbered SQL in `packages/db/migrations/neon/NNNN_*.sql`, split on `--> statement-breakpoint`, bundled with `import.meta.glob('?raw')`, with a committed checksum lock file and a CI test.
2. Use the in-house `migrate()` described above:
   - tracking table `toolbelt._migrations(version, name, checksum, applied_at, applied_by)`;
   - one `sql.transaction` per migration, starting with `pg_advisory_xact_lock(LOCK_ID)` and then the tracking INSERT;
   - checksum verification and an "older build" compatible mode;
   - expand/contract discipline.
3. Do **not** use drizzle's neon-http migrator or node-pg-migrate at runtime. drizzle-kit is optional for drafting SQL.
4. Locally:
   - WXT `defineItem` `version`/`migrations` for `chrome.storage`;
   - `idb` `upgrade` for IndexedDB structure;
   - a separate resumable data-migration step for anything encrypted;
   - the outbox is never dropped.
5. Test with PGlite in vitest: apply all migrations, apply them again as a no-op, then simulate two concurrent runners. Before release, run the same suite against a throwaway **Neon branch**.
