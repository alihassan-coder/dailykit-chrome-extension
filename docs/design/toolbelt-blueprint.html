Build order

  1. 1

    Foundations

    Git and a private GitHub repo. Workspace with WXT, TypeScript, React and Tailwind. A lint rule that stops modules importing each other. CI builds every target on each push. Changesets for versions: each tool has its own version, and Toolbelt has its own.

  2. 2

    Core, test-first

    Module registry (each tool declares its name, sites, permissions, features and settings), per-tool storage, the migration runner, an event bus between tools, the theme tokens and the UI kit.

  3. 3

    Shell

    Side panel as the main home, the dashboard (sort tools, switches, settings, appearance), a small popup for quick actions, and Ctrl K search across every tool.

  4. 4

    Cairn module

    Port the engine with its tests: page bridge, Claude and ChatGPT adapters, chat parsing, saving, lock. Redesign every screen in the new kit. Bring back the snippet fill-in form. Import existing saved chats once.

  5. 5

    Neon personal sync

    Paste your connection string once; only the background worker uses it. Each tool's SQL migrations run in order and are recorded. Sync is switched on per tool.

  6. 6

    Standalone builds

    Cairn built as its own extension from the same code. GitHub Actions produces release zips for Toolbelt and for each tool you sell.

How it stays manageable

      tests/
  docs/
    ARCHITECTURE.md
    research/
  • One folder per tool. Adding a tool means copying the template. It appears in the dashboard with its own switch, settings and version.
  • Tools only talk through core. No tool imports another, and the build fails if one tries. That is what makes selling one tool alone possible.
  • Small features are declared, not hidden. Each tool lists its features in module.ts, and the dashboard turns that list into switches.
  • Database changes are numbered files. Browser data and Neon tables both migrate in order, once, with a record of what ran. The dashboard shows the current version.
  • Every release has a version. A changelog entry per change, tags on GitHub, zips built by CI.

Still open: whether apps and packages become a full monorepo or one package with several build configs. The research running now decides it.
